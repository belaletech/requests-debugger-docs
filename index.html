See exactly where your test request stopped.

Requests Debugger sits between your Selenium or Appium test and the TestMu AI hub. It records every request, checks your network and machine, and tells you why a request never reached us.

Free · macOS, Windows and Linux · Beta

Why use it

Sometimes a test fails with session not created, connection reset, timeout or ECONNREFUSED, and the request never shows up on your TestMu AI dashboard. The cause is usually between your machine and our hub: a corporate proxy, a firewall, a VPN, DNS, an overloaded machine, or a network that drops the request.

Run your test through Requests Debugger and you get a clear answer, plus a log folder you can send to our support team.

Every request, recorded
Method, endpoint, status, timing and response for each call your test makes.
Connectivity checks
Can your machine reach the hub over HTTP and HTTPS, with and without your proxy?
Network details
Ping to the hub and the open connections on your machine.
CPU and memory
How busy your machine was when the run started, with the top processes.
Automatic retry
A request that fails inside the tool is retried once, and both attempts are logged.
One folder for support
Every run is saved as its own folder, ready to zip and share.

Install

The beta is not signed yet. The first time you open it, macOS and Windows show a security warning. The steps below show how to allow it once.
  1. Open the .dmg file and drag TestMu AI Requests Debugger into Applications.
  2. Open the app from Applications. macOS blocks it the first time.
  3. Open System Settings → Privacy & Security, scroll down, and click Open Anyway next to the message about TestMu AI Requests Debugger. Enter your password.
  4. The app opens. You only need to do this once.

Right-click → Open no longer skips this check on recent macOS versions.

  1. Run TestMu AI Requests Debugger-Setup-1.1.0-beta.3-x64.exe. It installs for your user only; no administrator rights are needed.
  2. If you see "Windows protected your PC", click More info → Run anyway.
  3. Start the app from the Start menu.

Prefer not to install? Unzip the portable .zip and run TestMu AI Requests Debugger.exe.

Debug a failing test

The whole flow, from opening the app to sending logs to support.

  1. Open the app

    Click Get Started. The version at the bottom confirms you are on the beta.

  2. Choose what you are testing

    This sets the hub the debugger forwards your requests to. You no longer need HUB_URL.

    • Mobile App / Mobile Web: Appium on real devices and emulators
    • Desktop Web / Linux Automation: Selenium browser tests
    • Custom Hub: a private relay, staging or regional hub

  3. Pick a folder for the logs

    Each run is saved as its own folder here, so you can come back to it later.

  4. Check the summary

    Confirm the platform, hub and log folder, then click Continue.

  5. Start the debugger

    Click Start Debugger. The screen shows the address your test should use: localhost:9688.

  6. Point your test at the debugger

    Change only the hub address in your test. Use http, because the debugger runs on your own machine.

    Before  https://USERNAME:ACCESS_KEY@hub.lambdatest.com/wd/hub
After   http://USERNAME:ACCESS_KEY@localhost:9688/wd/hub

    For Appium the "before" hub is mobile-hub.lambdatest.com; the "after" address is the same. See code examples.

  7. Run your test and watch it live

    The dashboard fills in as requests arrive: totals, failures, average duration and active sessions.

  8. Open a failed request

    In Requests, filter by Failed and click one. The app shows where the request stopped (client, debugger or hub), the error, and each retry.

  9. Stop and send the logs

    Click Stop Debugger. The run is saved under Runs. Click Open Log Folder, zip the run folder and send it to TestMu AI support with a short description of the problem.

    The log folder contains your access key. See Privacy.

Change the hub URL

Only the hub address changes. When you are done debugging, switch it back.

String hubURL = "http://" + username + ":" + accessKey + "@localhost:9688/wd/hub";
WebDriver driver = new RemoteWebDriver(new URL(hubURL), capabilities);
hub_url = f"http://{username}:{access_key}@localhost:9688/wd/hub"
driver = webdriver.Remote(command_executor=hub_url, options=options)
// wdio.conf.js
hostname: 'localhost',
port: 9688,
protocol: 'http',
path: '/wd/hub',
user: process.env.LT_USERNAME,
key: process.env.LT_ACCESS_KEY,

Command line (CI/CD)

On build servers, in Docker or in pipelines, use the command-line binary. It uses the same engine and writes the same log files as the app.

Get the binary

Download the command-line binaries

Pick the binary for your platform and run it in a terminal:

PlatformCommand
macOS (Intel; runs under Rosetta on Apple Silicon)./request_debugger_mac
Linux (x64)./request_debugger_linux_64
Windows (x64)request_debugger_win64.exe

On macOS and Linux, make it executable first: chmod u+x ./request_debugger_mac

Choose the hub

The binary uses the web automation hub by default. For Appium and real devices, set the mobile hub before you start it:

# macOS / Linux
export HUB_URL=mobile-hub.lambdatest.com

# Windows (cmd)
set HUB_URL=mobile-hub.lambdatest.com

Then point your test at http://USERNAME:ACCESS_KEY@localhost:9688/wd/hub.

Example: GitHub Actions

- name: Start Requests Debugger
  run: |
    chmod u+x ./request_debugger_linux_64
    HUB_URL=hub.lambdatest.com ./request_debugger_linux_64 --logs-path ./rd-logs &
    sleep 5

- name: Run tests through the debugger
  env:
    LT_HUB_URL: http://${{ secrets.LT_USERNAME }}:${{ secrets.LT_ACCESS_KEY }}@localhost:9688/wd/hub
  run: mvn test

- name: Upload debugger logs
  if: always()
  uses: actions/upload-artifact@v4
  with:
    name: requests-debugger-logs
    path: ./rd-logs/RequestsDebuggerLogs

The same pattern works in Jenkins, GitLab CI and Azure DevOps: start the binary in the background, run the tests against localhost:9688, and keep the log folder as a private build artifact.

Use it as a proxy instead

Rather than changing the hub URL, you can route traffic through the forward proxy on port 9687. In Java:

System.getProperties().put("http.proxyHost", "localhost");
System.getProperties().put("http.proxyPort", "9687");

Logs

Each run creates its own folder. Inside RequestsDebuggerLogs:

FileWhat it contains
Requests.logEvery request and response, with timing and retries
Connectivity.logReachability of the hub and automation.lambdatest.com, with and without proxy. Repeated when a request fails
NetworkStats.logPing and open connections (on Windows also the routing table and ipconfig /all). Repeated when a request fails
CPUStats.logCPU load and top processes at start
MemStats.logMemory and swap at start
RDT_Error.logUnexpected errors inside the tool

Reading Requests.log

Each request has a number (#2) and a unique ID. The ID is also sent to TestMu AI in the X-Requests-Debugger header, so our team can find the same request on our side.

TagMeaning
Request StartYour test's request reached the debugger
Request EndYour test finished sending it
Tool Request - Retries Left: NThe debugger forwarded it to the hub (retried once on failure)
Response EndThe final response sent back to your test
If a request has Request Start but its Tool Request fails with an error such as ENOTFOUND or ECONNRESET, it never reached TestMu AI. Connectivity.log and NetworkStats.log usually show why.

Privacy

Everything runs on your machine; the logs stay in the folder you chose. They describe your test traffic and your machine:

  • Requests.log stores requests in full, including the Authorization header with your username and access key.
  • NetworkStats.log and CPUStats.log list processes and network connections. On Windows, NetworkStats.log also includes ipconfig /all (adapter names, IP and MAC addresses).
Share the log folder only with TestMu AI support. If it was shared anywhere else, regenerate your access key in your TestMu AI profile.

Troubleshooting

"Port 9688 is already in use"

Another copy of the debugger is still running. Quit it (on macOS use Cmd+Q; closing the window is not enough), or change the port in Settings.

My test can't connect to localhost:9688

Check that the app shows Running, that the hub URL starts with http:// (not https://), and that the test runs on the same machine as the debugger.

macOS says the app can't be opened

Use System Settings → Privacy & Security → Open Anyway. See Install.

Windows shows "Windows protected your PC"

Click More info → Run anyway. The beta is not signed yet.

Linux: the app doesn't start on Ubuntu 23.10 or 24.04

Start it from a terminal with testmu-requests-debugger --no-sandbox, and let us know you needed this.

I'm behind a corporate proxy

Give the debugger your proxy details (CLI: --proxy-host, --proxy-port, --proxy-user, --proxy-pass). Connectivity.log then shows results with and without the proxy, which tells us whether the proxy blocks requests.

Get help

Contact TestMu AI support through the chat on your dashboard or by email, and attach the zipped run folder. Found a bug in the beta? Tell us your operating system and chip, and what you were doing.
